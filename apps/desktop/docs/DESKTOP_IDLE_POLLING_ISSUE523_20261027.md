## 可复现问题与修复

`createDesktopProactiveRuntimePump` 每次调用 `maintenancePage`，原实现先用 `listTasks` 水合普通任务，再逐条查持续工作流检查点。没有任何持续工作流也会重复处理普通历史。PR #522 将每轮限定为十页，但 1 万条任务下每次仍水合 1000 条；正常资源策略又每 120ms 触发一次维护。本次真实 SQLite 合成对照测得单轮 P95 386.680ms，足以使维护持续占用主线程。这证明一个与 Issue 相符的热点，未对用户原资料做 profiler，也不声称排除了所有其他热点。

- 启动恢复、维护页和对话工作流列表改用 Runtime 已有的 `listTaskCheckpointPage(..., ['desktop-proactive-workflow-v1'])`。原索引先筛选候选，再执行现有版本、任务身份、来源、隐私与镜像绑定校验。检查点存在本身不构成恢复或工具授权。
- 既有 120ms 入口继续处理事件与待办提醒。其他七项维护各自只保留一份未完成操作，完成后再等待维护间隔；一个慢宿主不占住其他宿主。正常／受限／严重资源压力下间隔为 1／2／5 秒；不追赶错过轮次，不自动重试副作用。
- 保留原有事件固定水位、每批 128 条、批间让出、任务读回恢复，以及快照 ACK／负 ACK／显式 resync。没有删除 Runtime 历史、审批、unknown 或 Evidence。

未更改 Core wire、Schema、依赖、数据库迁移、工具授权或 AgentArts 编排；接口成熟度不提升。维护适配器不创建计时器、任务队列或第二套 Scheduler。
