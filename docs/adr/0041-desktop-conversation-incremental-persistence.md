# 0041 Desktop 会话元数据的增量事务持久化

状态：**proposed**，2026-10-26。Profile：`huawei_ict_agentarts`。候选已包含 Main 最终退出接线；Windows Electron 分发和真实用户资料迁移仍未验收。

2026-10-26 云端接收补记：来源 ZIP 的 288 项任务文件、119 份基线原文及 32 项材料已按清单核验；基线原文的长度、SHA256、Git blob ID 均相符，但来源声明的 `b2fb20dd` commit 未能在本地或正常远端核实。接收方从 `934b7c44` 独立三方整合，属于未提交、未发布的审查候选，不能视为 Windows 原工程完整复原。A12 的 1724 项输入中仍有 65 项未随包交付且与当前 main 不同或缺失，因而无法完整复原来源的历史快照，包括其中既有 team/模型控制及部分 provider 守卫。该历史可复原性限制不等于当前候选缺少构建输入：当前候选独立根 build 已通过；来源回执与当前候选验证分开记录。

来源报告的实际 Root Main 旧 v4 合成资料迁移、正常退出与同资料重开已有独立回执；接收方核验了回执文件，未收到其完整原始日志，也未在 Windows 重跑。两项 v2 GUI smoke（native slider、PR376）仍 pending；PR376 使用生成 Main stub，不能证明实际 Root 生命周期。公共 SQLite Evidence 草案仍 pending，不能提升为通过。

## 背景与决定候选

`apps/desktop/electron/conversations.js` 保存 Desktop 会话、草稿、模型偏好、Live 正文及任务的 UI 归属链接。当前每次成功修改都同步复制相关 Map，并把全部消息序列化成一份 JSON，通过临时文件替换。隔离合成基线中，1 万条、每条 2 KiB 时，一次草稿修改仍重写约 21 MiB，耗时约 40～48 ms；该数据只代表相应 Node/Windows 夹具，不代表 Electron 或用户环境。

候选决定：保留 `Conversations` 的同步方法和内存读取语义，以可信主进程私有的 **增量 SQLite 事务后端** 替换整份 JSON 保存。沿用项目已有的 Node 内置 `node:sqlite`，不增加外部依赖。每次成功返回必须对应已提交的原操作；草稿批量关闭、归档与活动会话切换均在一个事务内完成。SQLite 仅保存原 `Conversations` 数据；`turns` 中的任务 ID、goal 和 conversationId 是 UI 链接，TaskRuntime 继续独占任务状态、终态、执行记录、审批、Evidence 与未知写入事实。不得新建任务执行库或让 UI 改写 Runtime 事实。

此决定以 Electron 内置 Node 的 `node:sqlite` 可用性、Windows 打包验证、迁移和失败恢复证明为前提。若不满足，应保持现有后端并重新评审。备选的增量文件日志需要帧校验、同步持久化、序号与操作回执、撕裂尾恢复、压缩事务和跨实例互斥；普通 JSONL 追加或异步保存不能保持本次同步确认语义，暂不采用。

## 不变的调用契约

- `new Conversations(file)` 可读取现有 v1～v4，`file === null` 的内存夹具仍可运行；输入无效应拒绝，不创建空白历史替代。旧 JSON 的只读构造不创建备份、数据库或标记，首次实际修改才启动迁移。对 `session`、`snapshot`、`preference`、`messagesFor`、`history`、`readMessageDisplayPage` 的返回形状、所有权、排序、时间戳和分页边界保持兼容。
- 导入时保留 sessions、turns、messages、preferences 各数组原始 ordinal；后续新增记录按现有 Map 插入位置追加，正文或元数据 UPDATE 保留原 ordinal，不能以 `REPLACE` 重建记录而改变顺序。`messagesFor` 按 `createdAt` 稳定排序，同时间戳沿用原 Map 顺序；消息分页继续使用 `createdAt` 加 message key 的确定性顺序。SQL 读取须显式 `ORDER BY`，不能依赖表扫描的偶然顺序。
- `create`、`switch`、`rename`、`archive`、`setDraft`、`flushDrafts`、`setPreference`、`add`、`addLiveMessage` 维持同步成功/失败语义。新消息 ID 冲突拒绝；同一身份和同一正文无写入；正文修订保留原时间与归属。批量草稿任一项无效时零修改。
- 当前主进程和测试直接读取 `turns`、`messages`、`sessions`、`preferences`、`messageRevision`，部分测试注入 `save` 或修改 `file`。实施前需决定保持只读兼容的内存视图，还是逐个迁移这些调用/故障注入点；不得只替换磁盘格式导致分页、任务归属或失败后的内存状态漂移。
- Live 语音恢复队列以 `addLiveMessage` 的同步确认决定是否清除待补记录；新后端不得在提交未知、失败或未读回时返回成功，也不能盲目重复可能已提交的写入。
- 退出时先完成当前的草稿预检与最终提交，再释放会话数据库。实际 `draftQuitPreflight.commit()` 会令页面保持 inert；显式 `cancel()` 可解除，`reportQuitFailure()` 已调用它。不能在 commit 后仅 `preventDefault()` 留下冻结页面。候选是在全部同步写入已确认、`before-quit` 已接受后，于最终 `will-quit` 释放无待写事务的连接；单纯 close 释放失败记录诊断并允许进程退出，不把 close 当作写入持久化回执。若仍选择阻断退出，必须先证明句柄可读写恢复，再显式 cancel；部分关闭而不能恢复时不得放行新的会话写入。实际接线和退出失败测试仍待实现。
- `main.js:176` 先取得单实例锁；`app.whenReady()` 在 `:4420` 对未得锁实例立即返回；`new Conversations(...)` 在 `:4501`，因此当前 Main 构造位于锁后。独立脚本和已经持有旧 JSON 内存的旧程序不受此保证；新库仍须 CAS，并在每次写前确认旧路径是本代标记，分歧时冻结写入。

## 首次迁移、兼容与回退

1. 可信宿主在**首次实际修改**时读取旧 JSON **原始数组逐条审计**，再用原加载器核兼容语义。原加载器会跳过无效 turn、以后项覆盖重复 `taskId`，也会覆盖重复偏好 key；仅看加载后的 Map 或由其计算摘要不能证明无损。每个源版本 v1～v4 须有明确字段/唯一性/计数检查，并拒绝词法重复 JSON 对象键、正文去空格或偏好字段丢失等静默变化。旧版时间戳的等价 ISO 表示可以沿用加载器的规范化；原字节始终保存在备份，且必须校验同一时刻。无法无损解释的项保留原文件并拒绝迁移。先在同一用户目录制作不覆盖的原字节备份，读回精确一致；备份确认或同步失败即停止，不改原文件。首次选择默认思考模式时另保留修改前的完整 v4 逻辑快照，不把 version-5 标记误当成可回退的正文备份。
2. 使用单独的 Desktop SQLite schema 版本，在一个受信 `BEGIN IMMEDIATE` 事务中导入 sessions/active IDs、完整 draft、messages、preferences 和 UI turns，并同事务写入导入代次、来源版本、原字节/备份摘要、逐类数量与全量语义摘要。摘要必须包含每个数组的原始 ordinal；同 `createdAt` 的 turns/messages 也须保留原有稳定顺序，不能仅按时间和 ID 重排。COMMIT 返回不明时先隔离原写连接，再由独立只读连接核数据库提交凭据、逐类数量与全量行；未提交事务里的可见值不能充当回执。读回不可用不得重导入、改旧文件或返回成功。已确认未提交且库内无孤立行才可从未改动的旧文件重试；已提交则保持同一代次，绝不再次导入。
3. 旧路径标记必须是原位 `conversations.json` 上**明确不受旧版支持的 `version`**。当前旧加载器实测拒绝 `version:5`；它会接受仅增加 `migratedTo` 字段的合法 v4，路径缺失时甚至会从空状态再写 v4。在新 DB、源和备份的完整语义读回确认前不开业务写；之后用同目录临时文件原子替换旧 JSON，绝不先删除旧路径，并对替换结果精确读回。**只有标记已确认，才提交引发迁移的首个业务操作**。若该业务操作在提交前失败，内存和数据库仍为原业务状态，旧源字节保留在备份，重开会从标记所指数据库读回；若其提交结果未知，冻结实例、独立读回原操作，不自动重试。提交后、标记前若中断，只在原 JSON 与备份原字节仍匹配且只读 DB 全量语义/代次均确认时恢复标记。标记替换回执不明则只读原位文件，不能盲重试。首次全新 profile 没有 JSON 时，只读构造同样不建文件；首次写入先独占创建并读回旧版拒绝的 `initializing` 标记，再建初始 DB。初始事务提交及独立全量读回后，才原位原子推进为 `ready`，随后才能执行业务写。重开时只允许 `initializing` 且 DB 缺失时按固定代次补初始库；`initializing` 且 DB 已提交时先核回执再推进。`ready` 后 DB 缺失或不可读必须拒绝，绝不从默认会话重建。部分标记或 DB 状态不可读时停机待核实。标记形状和 Windows 断电次序仍须生产测试。
4. 新版启动只接受原位完整标记、来源备份（全新 profile 除外）和数据库代次相互匹配的状态。旧程序写回 v4、旧文件消失、备份冲突、数据库损坏或版本高于当前程序时均显式拒绝自动覆盖。旧版可写回退没有自动承诺；需另做含新数据的核对导出/导入，并经用户确认。不能把迁移前备份当成当前历史直接运行，也不能给不识别标记的旧程序一个可写空路径。
5. 普通写入以一事务记录目标行、稳定操作身份和 revision，并复核旧路径仍为本代标记；在同一写事务中先核数据库 generation、来源摘要、schema 版本及全局 revision。提交前错误在 ROLLBACK 确认后不更新内存，允许调用方在条件修复后于同实例**显式**重试；首次旧源迁移若失败，只有原字节未变且空库或已提交导入经完整独立核对时才保留此重试能力，其余状态需重开核实。COMMIT 抛错时立即冻结原写实例，隔离原连接，再用独立只读连接按同一操作身份及目标行精确读回；绝不能用原连接里可能未提交的行确认成功。确认已生效方可成功返回，但该实例仍须重开后才能继续写；读回不可用或不匹配则保持待核实，不能盲重试。跨实例更新使用 CAS，拒绝旧 revision 覆盖。数据库的 `WAL`/`synchronous=FULL` 只能说明采用相应同步协议，不能凭配置推断所有硬件断电场景已验证；现有 JSON `writeFileSync` 加 `renameSync` 同样不等于 `fsync` 耐久承诺。

## 实施范围与验证门槛

最小候选生产范围：`conversations.js` 保持 API 与校验；新增私有 SQLite store 实现事务/迁移/读回；`main.js` 在已得单实例锁后的构造和最终退出阶段接线。SQLite 路径从受信 JSON 路径派生，`data-paths.js` 不变。隔离工作树已完成前两项和归属本包的会话、草稿、Live 恢复、分页、迁移测试；Main 的最终退出接线和两项直接读取 JSON 的 smoke 测试由另一个工作包交付，不属于此 ADR 的实现回执。

当前隔离证据须分层阅读：v2 小型状态机原型 14/14、旧 API 与候选的黑盒对照 49/49、真实受控子进程在 COMMIT 前后终止的合成夹具（前为全部旧数据，后为全部新数据），以及本工作树源码冻结的 Desktop 2140 项（2130 通过、0 失败、10 跳过）。这些作用域重叠，不能相加；受控终止不证明断电。首次迁移、CAS、未知提交、同一 WAL 快照、全新 profile 标记、清理句柄后的重开均有定向 Node 测试；尚需 Root 最终源码和 Main 接线共同验证。

同一份合成种子在 Node 24.15.0、Windows 上比较旧版与候选：1 万条、每条 2 KiB 时，12 次 append 的 P50/P95 从 49.05/56.92 ms 到 1.50/7.36 ms，12 次草稿修改 P50 从 43.12 ms 到 0.80 ms。48 次稳态保存的逻辑序列化 payload 从 1015.173 MiB 降到 0.060 MiB；这不是物理写入量。代价是首次候选迁移加业务写入 957.32 ms（旧版单写 69.67 ms）、候选峰值 RSS 336.391 MiB（旧版 158.492 MiB）、重开 195.07 ms（旧版 67.293 ms）。这组数据仅支持当前合成负载下的稳态延迟改善，不证明真实用户环境、Electron UI 响应或内存收益。

来源同一合成样本的后续重开重复值为候选 183～193 ms、旧版 56～65 ms；关闭后 marker、备份与 DB 合计 60.861 MiB，旧 JSON 为 21.154 MiB。WAL 净增 1,363,720 B 不等于物理写入量。全 canonical 消息 Map 仍常驻，不能宣传整体内存更低或启动更快。完整最新历史的 v5→v4 导出工具尚未实现；禁止删除 DB/marker 或直接恢复迁移前备份来假称保留迁移后的历史。`initializing` 状态下构造 Conversations 可能推进初始化，取证不能将其当只读入口。

本 ADR 不改公共协议或 Runtime 数据库迁移。首次真实分发还需 Windows Electron 内置 Node 与打包产物验证；真实用户资料仅在有备份、失败恢复路径和对应授权后迁移。
