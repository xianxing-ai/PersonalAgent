# Laya 严格同输入与单变量诊断（2026-10-15）

本目录只记录测试，不确定架构，不修改生产模型、权重、选择器、授权或工作流，不发布镜像。
目标为解释先前鹈鹕源文件读取判断的 4/8；并非评价全部 28 项业务或自主编码能力。

## 已验证结论

1. **这组错误来自模型接收到问题之后，不是本地 HTTP 或返回 ID 映射差异。**
   原选择器＋HTTP、相同原始 body 的裸 HTTP、同一 Agent 实例中的直接 SDK，共 24 次调用。
   八组三路对照的 payload、SDK 参数、token/marker 编码摘要、答案、概率全部一致；各路径均为 4/8。
   此结论只覆盖本组样本和当前本地三层，不等于全项目接线已经验收。
2. **修正输入和选项并未得到可靠判定。**
   干净状态中正确／错误样本仅改变 proposedRead.arguments.path；选项不再声称未经证明的“路径完全正确”。
   六组文件名、两种极性、两种顺序：A/B、candidate_0/candidate_1、read/review、yes/no 均为 12/24，
   match/mismatch 为 13/24。基本失效模式由原输入的“偏选第二项”变成“几乎总选读取”。
   单改合同 errorStack、短问题、状态对象/字符串、选项描述、目录 Schema，均未稳定修复。
3. **不能据此说模型完全没有区分信息。**
   干净 A/B 状态的 12 组配对，正确路径的读取分数均高于错误路径；分数 AUC 为 0.9375。
   但其默认 argmax 全部选择读取，且不同文件名的分数分布重叠。局部排序与可用的动作判定不同。
4. **一个事后发现、随后冻结的边界没有泛化成功。**
   只用原鹈鹕 seed 0 的四条分数，按 `(最小正例分数 + 最大反例分数) / 2` 得到 0.91565，
   在生成新文件名、启动新推理之前写入 plan。20 组新文件名 × 正反 × 顺序，共 80 条。
   默认 argmax 为 40/80（正例40/40，反例0/40）；固定边界仍为40/80（正例0/40，反例40/40）。
   新样本配对分数方向仅19/40，AUC为0.6765625。没有用留出结果重新调整边界。
   这是探索性假说的前置冻结留出测试，不代表广泛、独立随机抽样的质量评估。
5. **精度和窗口不能解释当前主要错误。**
   相同规范输入下，BF16→FP32 未改变24条选择，最大概率差为0.0084。
   原输入的完整窗口编码为1177/1180 tokens；改用 SDK 默认1024确实截断，但四条选择均未改变。
   正式接入对照使用完整相同编码，不以默认截断作为“直接 SDK 正确接入”。
6. **部分语义分类能工作，不能称为整个模型只有50%能力。**
   鹈鹕“动画不动／文件未加载”的独立功能正控为7/8，仍有一条受顺序影响。
   它是正控，不是和文件名比较只变一个因素的因果对照；没有将其与路径分数混算。

现有证据支持“当前 checkpoint 与精确路径比较／条件选路任务不匹配，默认判定不能直接信任；
输入和选项影响失效模式”。不支持“传输解码弄反了结果”“把一个门槛调高即可解决”，
也不能由这个很窄的任务推导“整体设计超过前沿技术”或“所有 Laya 场景不可用”。
将可精确计算的条件置于未验证的语义必经关口，是当前使用方式的风险；本轮只作诊断，不实施架构取舍。
这不能替代通知／升级、材料相关性、记忆排序、方案比较等真正语义任务的评估，也不据此取消常驻本地判断层或主／影子方向。
三路仍共用原厂 SDK；本轮没有使用独立推理引擎验证权重，不能继续细分成某层神经网络或上游 SDK 的具体缺陷。

## 方法、控制与统计口径

- 一次只加载一个现有 multilingual checkpoint；CUDA、Torch计算线程1、interop线程1。
- Laya 0.3.20，Torch 2.14.0+cu130，Transformers 5.17.0；主体 BF16 autocast，FP32 单独对照。
- 原权重清单先校验；序列化顺序、特殊选项 marker、实际 SDK 编码摘要均保留。
- 方案先生成完整计划并写 SHA256，再加载权重。标签、描述、问题、状态字段逐项隔离。
- 普通与新留出共52组正反配对，token编码摘要均不相同；没有发现不同文件名被编码成相同输入的情况。
- 对同一返回分数比较 argmax／固定边界，只改变后处理；没有改模型输出来追求通过。
- 452 次主体＋56 次补充＋84 次新留出/参照，共592次真实 SDK 调用。它们不是592个独立业务任务。
- 每次调用旁路重复编码以审计，耗时不是性能基准，不能用于150ms延迟验收。
- MaaS调用0，业务工具调用0，权重训练0，生产修改0，镜像发布0。测试进程结束后退出。

## 输入问题与协议更正

第一轮保存于本机 `.cache/laya-controlled/run-LAEX9T`，共452次。
复核发现两项测试字段名错误：原输入短问题应引用 targetFile，规范夹具合同应引用 requestedFile。
更正后主体保存于 `.cache/laya-controlled/run-ZOqyAH`，本目录采用该轮；未改变的348条变体编码和答案逐项完全相同。
第一轮受更正影响的28条不进入最终因果结论，原始记录保留。

主体中的 `downstream_goal` 将原 pelican.svg 目标原样加到其他文件名上，会形成旧目标冲突。
它是陈旧上下文压力测试，不能称为干净的“无关长上下文”准确率；summary已作标记。
补充轮将所有文件名与当前请求对齐，只增加一个下游目标字段：12/24，修复5条也破坏5条，没有净改善。
