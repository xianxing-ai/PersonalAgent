# F16/F17 Linux 提供者接线与验收（2026-10-31）

范围：PR #531 的 `huawei_ict_agentarts` F16/F17 受信来源与 Desktop configured-workflow ports。独立分支 `codex/pr531-f16-f17-cloud`。首包基线为 `43d0d370`；续包已合入 `08034ae4`，使用公共 `readConfiguredWorkflowBinding`、`createWorkflowBusinessToolBridge` 和 `readWorkflowBusinessToolSource`，不另外实现 worker、bridge 或授权层。

本包不表示 Desktop main 已装配、真实 AgentArts 整图已验收或 #531 可合并。续包提供固定图配置与逐节点 completion verifier；共同入口、真实 workspace/许可/测试意图审核服务和固定 AgentArts deployment 仍由主对话整合。缺失服务时工厂保持 unavailable。本包不修改云环境配置、不发布云环境、不更新 #531 原分支、不合并 PR。

## 生产行为

- F16 校验三条原 `github.actions.run.list/job.list/log.read` 的 Runtime 执行记录、原 child/parent/command、参数摘要、scopeRef、工具版本、confirmed 结果和 Evidence。仅接受同一 repo、失败且 completed 的 run/job、明确 job.runId 与所选 HEAD。外来任务、替换参数和 unknown 回执不可使用。
- `createF16CiFailurePorts` 冻结每个 parent/session 的选择与来源快照。direct 来源仍核验原双向边；nested 来源仅调用公共 helper 核验 graph→host→business 的精确双向边、marker、action、descriptor 与参数，不接受任意祖先。
- `createF16HeadReader` 在原 host child 预留 `workflow.head.<stage>.<sequence>` action；execute、before_export、after_export 分开，F17 命令增加 before_command/after_command。桥自行派生固定 commandId，调用方不伪造它。每阶段最多 32 次读；上一 action confirmed 后才分配下一序号，unknown/中断保留原 action。回读已完成 marker 时重新验证原来源，不能改 marker 跳过未知读。
- F16 执行后保存 `f16:ci-failure:<operationId>` 来源快照。出机许可 await 后重新读取原来源和新 HEAD；完成回执导出时还校验原 child 的 confirmed 输出和持久来源快照，禁止用相同文本替换另一条来源。
- F17 生产组合用 `createF17ObservedCommandTool` 包装既有命令实现，保留同一 descriptor/Policy/Gateway。N03 执行内先经业务桥读取 HEAD，持久预留观察记录，再调用原命令一次，保存实际调用起止时间/结果摘要，最后读取 HEAD。N03 confirmed 后只绑定已有观察，N04 不补造前后读回。旧 direct prepare/bind 端口保留供独立原来源使用。配方来自与 `createWorkspaceCommandTool` 相同的受信配置，不保存环境变量值。
- F17 使用现有 `locateTestFailures`，关闭源码片段读取。原失败输出仍保存在原 tool-result checkpoint，新的本地报告保存原来源、输出摘要、命令版本/配方摘要、HEAD、指纹及解析出的调用栈。没有第二套执行器或任务库。
- `f17:failure-report:<operationId>` 只写入原报告 child。对外投影只有计数、内容寻址 reportRef 和 `all6PassResolved:false`，不会把失败定位说成测试已修复。导出前后重新检查命令与版本来源。unknown 保留原 child，读回不重跑复现命令。

`F16SourceRead` 精确形状：

```ts
{ taskId, runId, toolVersion, scopeRef, arguments }
// taskId 是原 source child；runId = scopeRef = 'host-tool-' + taskId。
// arguments 必须和该 child 原 host-tool-intent 及参数摘要完全一致。
```

`F16HeadRequest` 精确形状：

```ts
{ actionKey, stage, toolName: 'workspace.git.head', toolVersion: '1.0.0',
  arguments: {repository}, deadline }
```

`invokeWorkspaceHead(scope, request, context)` 生产实现调用 `bridge.invoke({actionKey:request.actionKey,input:request.arguments},context)` 并返回 confirmed 原引用。桥按原 source host/run/action 派生 commandId。direct 测试/旧端口则绑定确切的 `scope.localTaskId + ':' + request.actionKey`，不能拿 nested 回执冒充 direct。pending、拒绝、unknown 不得伪造成字符串结果。权限由现有 Policy 授予，提供者自身不签发授权。

F17 `recipes` 必须与实际命令工具使用的不可变配方表相同。`beforeHead` 在 prepare 前完成，原命令在 prepare 后分派，`afterHead` 在原命令完成后取得；HEAD 与限定文件指纹不一致时拒绝报告。指纹覆盖范围由已有 Git 工具的受信 allowedPaths 定义，不能据有限文件指纹宣称整个工作区具有不可变隔离。

两个 host 还需原同步 `assertCurrent(scope, context)`、`requiredScopes`、`now`、精确目的地 `authorizeExport`。独立 F16 direct 组合对已绑定选择调用 `ports.assertSelectionCurrent(scope)`；Desktop 工厂则先核验公共图绑定，在 N01 真实读取后冻结选择，并在后续 frontier/completion 重验它。F17 的 workspaceRoot 是对应原命令的受信目录。configured worker 的 receipt-stage `authorizeExport` 必须调用对应 host.authorizeReceipt，并传入原 localTaskId/runId/scopes/authorizationRef/deadline/signal 与原结果，不能仅检查 `true` 常量。

configured-worker 采用既有 `RuntimeConfiguredWorkflowOptions`。F17 resolver 委托公共 binding reader 选择原 pending worker；只检查 F17/session/deadline/configurationVersion，不读取或复制 worker 私有命名空间。

## Desktop 续包装配契约

`apps/desktop/electron/f16-f17-workflow-ports.js` 导出：

```ts
createF16F17WorkflowPorts({
  runtimeModule, getApplication, images: {F16?, F17?},
  workspace: {root, recipes, commandTool, available(workflowId, scope),
    readSelection(workflowId, scope), assertCurrent(workflowId, scope), patchReconciliation?},
  authority: {available(workflowId, scope), assertCurrent(workflowId, scope)},
  authorizeExport({taskId, workflowId, stage, value, deadline, signal}),
  f16TestIntent?: {tool, available(scope), verifyReceipt({taskId, deadline, signal, input, patch, review})},
  now?: () => Date,
})
// -> {tools, configuredWorkflowWorkers, commandTool, workspacePatchReconciliation, unavailable}
```

根使用返回的 `commandTool` 替换原 tools 数组中的唯一 `workspace.run_allowed_command`，再加入 `tools`；将 `configuredWorkflowWorkers` 传给 Runtime。F16 还要求原 workspace 提供真实 `patchReconciliation:{bindingId,reconcile}`，并将同一返回端口接到原 Runtime `workspacePatchReconciliation` 选项；缺少端口时 F16 absent，不绕过已有恢复绑定。`getApplication` 支持先建配置后创建 Runtime，不需要假 Runtime。images 每项须有真实 `bindingId/advance/receiptSecret/available`。authority 与 workspace 的同步 gate 必须返回 void，并检查实际当前许可、工作区身份与配置撤销；异步 gate 拒绝。workspace.available 必须确认原来源、目录、配方及执行依赖确实可用。所有服务等待携带原 signal/deadline，并使用有界等待。

最外层服务缺失时仅返回空 tools/workers 与 unavailable；根仅在返回 commandTool 存在时替换原工具，并保留原 workspace 端口，不把 unavailable 组合当成删除现有工具的指令。

根需从公共 application 出口导出 `createF16CiFailurePorts`、`createF17ReproductionPorts`、`createF17ConfiguredDriverResolver`、`createF17ObservedCommandTool`、`createF16HeadReader`、`readF16Source`、`awaitF16Port`；既有两个 host 与业务桥/helper 已有公共出口。生产 Desktop 只消费注入的公开 runtimeModule；测试暂时注入相同编译模块以避开根文件所有权。

固定工具及严格 request/input/result schema 由深冻结 `F16_F17_CONFIGURATIONS` 发布，配置版本 `f16-desktop-v2` / `f17-desktop-v2`。request 都为 `{selectionRef}`，未知字段拒绝。GitHub 使用公开 `GITHUB_CONNECTOR_VERSION`，其余固定 1.0.0；不能由模型替换工具清单或版本。输入来自受信 `readSelection`，首次冻结后不得替换：

- F16 选择：`{selectionRef, repository, headSha, runId, jobId, patch:{path,expectedSha256,edits:[{oldText,newText}]}, recipeId}`。
- F17 选择：`{selectionRef, repository, headSha, recipeId, sourceSessionId, initialFailure:{command,beforeHead,afterHead}}`；三个原回执属于当前 parent task，按真实时序绑定相同 repo/HEAD/文件指纹，命令非零退出。仅把经过验证的失败输出与来源摘要写入严格图 input。foreign task、缺失版本或非法时序拒绝。

frontier 逐节点固定工具、版本、参数和已完成依赖；必须存在原本地依赖回执，镜像把节点标为 completed 不够。决策上下文必须匹配本图/节点/原 input 与候选 ID；原选择 abstain 时禁止后续执行，F16 修复选择还必须明确 legitimateFix=true。F16 应用补丁前重新读取原失败节点绑定的真实 HEAD，N05 前验证原测试意图审核；F17 N03 的参数只能是所选 recipeId。F17 completion 逐条读公共 confirmedOperations，核验原报告、命令、观察时序与来源，不把失败定位报成修复成功。

F16_N04 必须提供真实注册的 `workflow.host.f16_n04@1.0.0` 与独立原回执验证服务，结果至少包含 `noCheatingDetected:true` 和精确 `patchDigest=sha256(JSON.stringify(input.patch))`；无服务时整个 F16 配置 absent，不以测试未改/断言数量代替验收意图审核。N05 固定配方必须真实执行并以 stdout JSON 返回 `{repository,headSha,runId,jobId}`，新 head 不得等于原失败 head。completion 再经原业务桥读取 GitHub success run/job，核验实际 HEAD、对应 run/job 与 run 创建晚于原补丁，并要求原命令 exitCode=0。仅本机测试退出 0 不足以完成 F16；本包没有触发真实 CI 或替用户生成该回执。

receipt 与 completion 出机均等待根的统一许可，再核对原回执/报告/版本；completion 前后读取新的 HEAD/指纹。未知操作不重放。根必须将出机函数接到原审批卡；本工厂不会给工具签发权限。

v2 使用新的来源投影和阶段 reservation；不把旧 v1 checkpoint 静默升级成当前证明。SQLite 恢复测试分别覆盖原直接报告 child 的审批恢复、完整 configured 结果持久化以及 nested unknown 保留原 child、不重放。未声称进程死亡后仍可恢复一个正在等待 nested 审批的进程内父执行；通用业务桥对此保持原有 fail-closed 语义，恢复策略由其负责人统一处理。
