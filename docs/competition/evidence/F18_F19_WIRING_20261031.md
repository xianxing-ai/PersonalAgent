## 生产路径与边界

`packages/connectors/github/src/f18-f19.ts` 通过原 `GhCommandRunner` 和原受限
`readToken` 发起 github.com API 请求，不新建凭据、任务库、执行器或重试器。
公开 `createGitHubF18F19Tools(options): RegisteredTool[]` 独立 opt-in，默认原 GitHub
`register()` 清单不扩大。输入/输出使用严格本地 Schema；凭据不进入参数、结果或错误。

| 工具 | 实际行为 |
| --- | --- |
| `github.bound_pr_diff` | 同仓库原 PR、head/base SHA 读前读后核对；完整且至多 65,536 字符的实际 diff、摘要与统计 |
| `github.current_head_merge_gate` | 实际 GraphQL 当前 head/base、非作者 User 批准、技术检查、未解决讨论、draft/冲突/主线状态 |
| `github.registered_merge` | 重读实际 gate 与 PR 后，对原编号发送 `PUT /merge`，body 固定原 head SHA 与所选 merge method，再 GET 核对实际 merge SHA |
| `github.merged_pr_readback` | 仅 GET 原 PR，返回目标当前合并状态；不证明本次 unknown 写入由本任务执行 |
| `github.issue_snapshot` | 仅 GET 同仓库原 Issue 编号、规范 URL、`updated_at`；拒绝 PR 冒充 Issue、旧版本与超限内容 |
| `github.issue_close_readback` | 仅 GET 原 Issue 当前关闭状态；不授予 close 权限 |

没有注册 `github.registered_close_issue`。缺原问题修复关联和独立回归时，提供可直接关闭
Issue 的工具会形成绕过缺失门槛的入口。

F18 合并门槛要求全部成立：当前 PR 为 OPEN、非 draft、同仓库 head/base；
`MERGEABLE` / `CLEAN` / `APPROVED`；明确配置的合资格非作者、真实 `User` 的当前 head
批准；无 Changes Requested、无未解决线程；完整当前 commit status rollup；每个配置的
required check 存在且成功，观察到的全部检查也成功。分页未完整读取、缺 check、旧 head、
机器人或作者自批、skipped/neutral/pending/failure 都不合并。
该实现保守地要求批准的 commit 等于当前 head，未实现 Owner 审核例外或历史批准保留放宽。
不会向 GitHub 提交批准、伪造 check 或绕过技术 CI。

GitHub merge API 只接受 head SHA 条件；客户端读取所有门槛与 PUT 之间不是服务端原子事务。
服务端分支保护/规则仍须正确配置，不能以本工具代替 GitHub 的执行时保护。
合并后 base 可能已推进，读回核对原 head 和实际 merge SHA，不把正常 base 推进当原 head 变化。

## 实际 Desktop / Runtime 消费

`createDesktopF18F19WorkflowPorts` 在缺任一受信来源时返回空 tools / workers：

```js
createDesktopF18F19WorkflowPorts({
  getApplication,
  github: {createTools, available, assertCurrent},
  selection: {configurationRef, readSelection, assertCurrent},
  requiredChecks, eligibleReviewers,
  authorizeExport, requestPresence,
  now: () => new Date(),
})
```

`selection.readSelection(scope)` 必须从用户明确的原生选择读取精确
`{repo,prNumber,headSha,baseSha,mergeMethod}`；`assertCurrent` 同步检查原选择/配置修订、
工作区和撤销。worker 请求须与该选择全等，不能用模型参数充当受信选择。
requiredChecks 与 eligibleReviewers 也必须来自明确原生配置；本包不写死示例值到生产。

`createF18ReviewConfiguration({userData,safeStorage,readRepositoryBinding})` 提供实际原生配置来源。
`readRepositoryBinding()` 从现有配置返回 `{repository,bindingId}`；
`configureFromNativeSelection({selection,requiredChecks,eligibleReviewers})` 仅供 Main 原生用户事件调用，
使用现有 Electron safeStorage 保存独立偏好密文，拒绝 task/run、approve、CI result 等额外字段。
`createPorts(options)` 捕获原配置 revision、repo/workspace binding 与三项精确选择，内部调用上面的
worker 工厂；配置变化/工作区变化/关闭/加密不可用立即失效，不能用新配置恢复旧图。
完整原配置（含 revision）的 SHA256 是 `selection.configurationRef`；worker 的
`configurationVersion` 包含该摘要，原 Runtime 持久 binding 因此在重启后也拒绝替换配置。
内部文件读取有界，拒绝文件 symlink、父目录 symlink/junction 和加载期间身份变化。
无路径进入 Renderer/model。该设置不是任务库、凭据层或授权。

`github.createTools({requiredChecks,eligibleReviewers,beforeWrite})` 消费根组合提供的
`developerDeployment.host.createF18F19Tools`。根组合应在原 provider options 的闭包复用
runner、readToken、repository，并保留原 current/readiness、任务/revision 与写互斥。
本包不读取或导出该闭包的秘密；该根共享文件由主代理串行接线。

根实际组合调用 `createConfiguredDesktopF18F19WorkflowPorts({getApplication,codingWorkspace,
developerDeployment,reviewConfiguration,authorizeExport,requestPresence})` 即可。
该专属 adapter 从原 workspace/developer snapshot 固定 repo、root 与 bindingId，检查原 Runtime
task/deadline/conversation，并消费原 `github.pr.get` availability 和 `host.createF18F19Tools`。
Main 不需手写恒真 current/available 或重建 provider；缺任一真实公开口返回 unavailable。

工厂返回 `tools`、`configuredWorkflowWorkerPorts` 和 unavailable。
F18 worker 名称为 `workflow.f18.review_merge@1.0.0`，配置版本 `f18-github-v1:<原配置SHA256>`。
Main 将 ports 合入原 `configuredWorkflowWorkerPorts`，由 AgentArts 使用同一 owned image 装配；
本工厂不创建 image，也不另建运行循环。

路径为原 Engine → configured worker → 原 HostBridge/Policy → `workflow.host.f18_*`
→ `createWorkflowBusinessToolBridge` → 原业务子任务 Policy → GitHub 适配。
N01 导出真实有界 diff；N02/N03 审查候选必须绑定原 head 和 diffDigest，阻断项非零不推进 N04/N05。
受信 `resolveInput` 在内部 graph input 加入固定 `reviewRequirements`，明确向现有 AgentArts
候选生成器说明 N02/N03 的上述字段；用户请求、原生选择和真实 merge 参数不接受该字段。
该要求只规定审查数据格式，不要求模型返回“无阻断”，更不构成写入授权。
N04 读取真实 GitHub gate；N05 重读 gate 后按原授权合并；completion 独立 GET 实际 merge SHA。
所有读取/写入的来源证明沿原 SQLite graph→host→business 双向边校验。
Runtime F18/F19 原 host 工厂已改用公开 `readWorkflowBusinessToolSource`，拒绝借用其他图/宿主的 confirmed 回执。
F18 回调兼容增加 `ToolContext` 参数，N01 输出增加必需 diff/diffDigest；需同步消费者的 export projection。

### 原授权卡与在场证明

`beforeWrite(operation,input,context):void` 是同步持久钩子，operation 为 `registered_merge`。
它检查原 graph、原宿主、原业务 child、当前配置、已确认审查/gate 与正在执行的独立 Policy allow，
再在原工具任务保存 `f18:original-github-merge-attempt`。已有 attempt 拒绝再写。

工厂提供 `prepareMergeQuestion(scope,question)` 与 `confirmMergePresence(scope)`。
Main 原 `requestToolAuthorization` 必须先调用前者准备原卡，在原卡决定 `allow_once` 后调用后者。
后者调用注入的原 `requestPresence(scope)`，完成前后重验来源；不能使用父图的存在性回执。
业务 merge descriptor 保持 `requiresPresence:true`。无 requestPresence 不启 F18。

### Unknown 与恢复

已分派后的异常、断连、超时、损坏响应、GET 核对失败都为 RESULT_UNKNOWN，不重试。
原业务 child 和宿主保留 waiting_reconciliation，原 SQLite attempt 保留。
`readUnknownMergeInspection(taskId)` 只返回与原 execution/input/source 对应的只读请求，
须由调用者继续通过原 Policy 执行。
即使读到 PR 已 merged，也仅表示目标状态一致，原写仍 unknown；不自动 finalize、不推定归因，
不以新 task/run 重放写入。本包未实现外部归因证明或自动完成原 unknown。

## F19 缺项与精确继续入口

完整 F19 worker 当前不注册，unavailable 为
`f19_original_f15_enqueue_and_independent_bug_regression_unavailable`。
`f15-review-config-host` 只证明原 task/session/snapshot/patchDigest 的签名审核选择；
现有 issue-triage/CI 修复接口也未提供 F19→F15 的原图关联与 merge 后原问题独立复验。
PR merged、模型“修好”、fixture 通过均不能补齐这些来源。

后续应沿已有公开 Runtime/Policy 与原任务 checkpoint 提供：

- `enqueueIssueRepair(scope, context)`：从原 Issue 编号、版本/内容摘要、原 F19_N02 决策绑定原 F15
  子任务，返回其 taskId 与原双向 task/operation/session 来源；重复读取不得再创建子任务。
- `resolveMergedReadback(scope, context)`：原 F15 修复子任务、关联 PR 与实际 merged SHA、原问题
  独立回归命令/recipe、执行前后 checkout SHA、真实退出码/行为结果和原 sandbox execution 的
  confirmed 来源。必须复核原问题、当前版本和实际测试，不能只返回 `verified:true`。
- 只有上述来源被原宿主核验后才实现/注册安全关闭工具，绑定原 Issue 最新版本并真实读回；
  unknown 保持原操作先核对，不重新 close。
